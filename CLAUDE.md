# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Docker image that runs Claude Code persistently on a host with Docker (developed against a Synology NAS), reachable over SSH, a web terminal (wetty — a real SSH client running in the browser, not a pty-exec tool like ttyd), and a web file manager (filebrowser). Sessions survive disconnects via tmux. See `README.md` for user-facing deployment/usage instructions — this file is about developing the image itself.

## Commands

There is no automated test suite, linter, or CI config in this repo. Verification means actually building the image and exercising it.

```bash
# Fast syntax check before a full rebuild (rebuilds are slow)
bash -n entrypoint.sh

# Build (default: latest claude-code, dev UID/GID 1000)
docker build -t claude-code-docker:test .

# Build for another arch (NAS may be ARM)
docker buildx build --platform linux/arm64 -t claude-code-docker:test --load .

# Build with a pinned claude-code version (tests the pre-Bun fallback path)
docker build --build-arg CLAUDE_CODE_VERSION=2.1.112 -t claude-code-docker:test .

# Smoke test the CLI without starting supervisord/sshd/wetty
docker run --rm --entrypoint sh claude-code-docker:test -c 'gosu dev claude --version'

# Full local run: copy .env.example to .env, point the *_PATH vars at scratch
# directories (not real NAS paths), then:
docker compose up -d --build
docker logs claude-code-docker
```

For interactive checks (SSH login, tmux auto-attach, filebrowser HTTP auth), there's no `sshpass` in the base images used for testing — spin up a throwaway `debian:bookworm-slim` container with `--network host`, install `expect` + `openssh-client` in it, and drive an `expect` script against the published SSH port. `curl` against the filebrowser port covers its non-interactive auth check (`curl -X POST .../api/login ...`).

wetty needs a real browser, not `curl` — its auth prompt renders inside an xterm.js canvas, so `document.body.innerText` reads empty and there's no REST endpoint to hit. Use Playwright's own Docker image (`mcr.microsoft.com/playwright:v1.48.0-jammy`, has Chromium + all system deps preinstalled — plain `npx playwright install --with-deps` fails in sandboxes without `apt-get`) against `--network host`, `npm install playwright` into a bind-mounted scratch dir first (the image has the browsers but not the npm package itself), then a short script: `page.goto()` the wetty URL, `page.click('.xterm')` to focus, `page.keyboard.type(...)` + `Enter` for the password, `page.screenshot()` to actually see the result (text extraction doesn't work, screenshots do). This is how the SSH-auth redesign was verified end-to-end — real login showing `dev@<hostname>:~$` plus the tmux status bar, and a wrong password showing `Permission denied, please try again.` and re-prompting, both confirmed visually.

To test changes to `getrandom_shim.c` without access to a genuinely old kernel, simulate one with a seccomp profile that returns `ENOSYS` for `getrandom`:

```json
{"defaultAction":"SCMP_ACT_ALLOW","archMap":[{"architecture":"SCMP_ARCH_X86_64","subArchitectures":["SCMP_ARCH_X86","SCMP_ARCH_X32"]}],
 "syscalls":[{"names":["getrandom"],"action":"SCMP_ACT_ERRNO","errnoRet":38}]}
```
```bash
docker run --rm --security-opt seccomp=<that-file> --entrypoint sh claude-code-docker:test -c 'gosu dev claude --version'
```
Without the shim this reproduces the real crash (`panic: getrandom failed: errno 38`); with it, `claude` should run normally.

Always clean up test containers/images/scratch dirs after manual verification (`docker rm -f`, `docker rmi`, `rm -rf` on scratch paths) — nothing here is meant to linger.

## Architecture

### Multi-stage Dockerfile
1. `shim-builder` stage: compiles `getrandom_shim.c` with gcc, kept isolated so the final image doesn't carry a C toolchain.
2. Final stage (`debian:bookworm-slim`): installs sshd/tmux/docker-CLI via apt; installs Node.js (LTS, NodeSource) + `wetty` via npm (global install — wetty is a fixed dependency of the image, not a per-project version, so unlike nvm/pyenv this doesn't need to be user-space; needs `python3` + `build-essential` from the base packages too, since wetty's `node-pty` dependency has a native addon compiled via node-gyp at install time — confirmed empirically, `npm install -g wetty` fails outright without them); installs `filebrowser` as a static binary downloaded per-architecture in a Dockerfile `RUN` step (not packaged for Debian) rather than via apt; creates the `dev` user with UID/GID pinned via build args (not left to `useradd` defaults, so bind-mounted file ownership survives rebuilds); copies in the compiled shim, `entrypoint.sh`, `supervisord.conf`, `sync-dev-password-hash.sh`; wires the latter into `/etc/pam.d/common-password`. `claude` itself is installed via Anthropic's native installer (`curl -fsSL https://claude.ai/install.sh | bash -s -- "${CLAUDE_CODE_VERSION}"`, run with `HOME=/etc/skel`) — see the home-directory seeding bullet below for why, and for why this isn't npm-based at all (unrelated to the Node.js that's now back in the image for wetty's sake — `claude` itself has no Node dependency anymore).

### Runtime flow: entrypoint.sh → supervisord → {sshd, wetty, filebrowser}
`entrypoint.sh` runs once as root at container start, does first-run/every-boot setup, then `exec`s into `supervisord` (which becomes PID 1's replacement and supervises the three long-running services). Order of operations in `entrypoint.sh` matters and is worth reading top to bottom before editing it. Notable pieces:

- **Home directory seeding**: bind mounts (see below) aren't pre-populated from the image the way named volumes are, so entrypoint.sh manually `cp -rn`s `/etc/skel` into `/home/dev` on first use — this is where the tmux auto-attach `.bashrc` snippet and the nvm/pyenv setup below come from. Gated on `.bashrc` not already existing in `/home/dev`, so **this only happens once, ever, per `DEV_HOME_PATH`** — anything later added to `/etc/skel` (e.g. nvm/pyenv, added after some users' homes were already bootstrapped) does *not* retroactively reach already-initialized homes on a rebuild; that requires manually copying the new `/etc/skel` content across. Don't assume a Dockerfile change here reaches existing deployments without telling the user.
- **`claude` CLI lives in `~/.local` (native installer), not npm at all**: originally installed via `npm install -g`, which put it in a root-owned tree (whatever prefix Node's own install resolves to, `/usr` here) — but `claude` only ever runs as `dev`, and its built-in auto-updater needs to overwrite its own installed files in place, which fails outright as `dev` against a root-owned tree (`Auto-update failed: no write permission to npm prefix`, reproduced against the real binary). First fix attempt: `npm install -g --prefix=/etc/skel/.npm-global`, keeping npm but redirecting the global prefix into the `/etc/skel` seeding mechanism nvm/pyenv already use — genuinely `dev`-owned via the normal home-directory bind-mount path, no `/usr` chown needed (an even earlier draft did `chown` part of `/usr` to `dev` directly and was caught in review as a bad tradeoff). That shipped, but got second-guessed immediately after: is `npm -g` even the right mechanism, or does `claude` actually expect/require it? **Checked by extracting real strings from the actual compiled binary** (`npm pack @anthropic-ai/claude-code-linux-x64`, `strings` on the resulting `claude` ELF) rather than assuming — it turned out the binary has explicit first-class support for (at least) four install methods (`npm-global`, `npm-local`, `native`, `development`), each with its own update codepath, and its own bundled guidance actively steers people *away* from npm and toward Anthropic's own installer: `"Consider using native installation: \`claude install\`"`. So the real fix isn't about npm's prefix at all — it's Anthropic's native installer (`curl -fsSL https://claude.ai/install.sh | bash -s -- "$CLAUDE_CODE_VERSION"`, confirmed by downloading and reading the actual script), which needs no Node/npm whatsoever (pure curl+bash, downloads a platform binary, verifies its SHA256 against a manifest, then runs `<binary> install` to place itself and wire up shell integration) — this let Node.js's whole apt dependency be dropped from the Dockerfile entirely. Installed with `HOME=/etc/skel` at build time, landing under `/etc/skel/.local/share/claude/versions/<ver>` and `/etc/skel/.local/bin/claude`, seeded into `/home/dev` the same way as before.
- **The native installer's own symlink needed a fixup**: `~/.local/bin/claude` is created as an *absolute* symlink to `$HOME/.local/share/claude/versions/<version>` — literally whatever `$HOME` resolved to at install time (`/etc/skel` here), the same class of bug hit earlier with nvm's install script hardcoding `$NVM_DIR`. `entrypoint.sh` recreates it as a *relative* symlink (`../share/claude/versions/<version>`, resolved by listing the `versions/` directory) every boot — cheap and idempotent, so it self-heals regardless of whether the version came from a fresh skel copy or the migration path below. No `.bashrc`/PATH wiring needed this time (unlike the npm-global attempt) — `~/.local/bin` is already on `$PATH` via Debian's stock `/etc/skel/.profile`, confirmed by reading it directly rather than assuming. Unlike nvm/pyenv (left as a manual migration for pre-existing homes — see above), this one gets an explicit unconditional-every-boot backfill in `entrypoint.sh` (copy `.local/share/claude` + `.local/state/claude` in if missing, both idempotent) since `claude` itself is core functionality, not an optional extra, and the user's actual production container was already hitting the original permission error. Verified end-to-end, several times over the course of this redesign: fresh boot has no `claude` anywhere under `/usr` and no Node/npm installed at all; `dev` can write into `~/.local/share/claude/versions/` (the exact operation that was failing originally); a simulated pre-existing home (real `.bashrc` + `.profile` sourcing it, no `.local/share/claude`) gets backfilled automatically with a correctly-relinked symlink and resolves `claude --version` over a real interactive SSH session on the very next boot; `CLAUDE_CODE_VERSION` pinning to an old version (`2.1.112`) actually installs that exact version (not latest) and `DISABLE_AUTOUPDATER=1` still reaches the SSH session correctly.
- **Password resolution — hash only, never plaintext, at rest**: `PASSWORD_HASH_FILE` (`/var/lib/claude-code-docker/.password_hash`, bind-mounted via `DEV_SECRETS_PATH`) holds the same kind of hash `/etc/shadow` would (yescrypt on Debian 12). If it exists, that's not a first boot — reapply it as-is via `chpasswd -e` (installs a pre-hashed password, no re-hashing/plaintext involved). If it doesn't exist, resolve a plaintext password once (an older version's leftover plaintext file, `DEV_PASSWORD`, or a fresh random value shown exactly once via `docker logs`), apply it with plain `chpasswd`, then persist only `getent shadow dev`'s hash field and let the plaintext fall out of scope. This whole dance — reapplying *something* every boot, not just first boot — exists because `/etc/shadow` lives in the container's own filesystem, not a bind mount, and does **not** survive container recreation (`docker compose down`/`up`, image rebuild, etc.) the way `DEV_STATE_DIR` does. An earlier version only called `chpasswd` on first run, which silently left `dev` with no usable Linux password after any recreation of an already-bootstrapped container — confirmed via a real repro (build buggy version → boot once → `docker rm` + recreate → SSH login rejected) before fixing it to run every boot.
- **Went from persisted plaintext to persisted hash — two escalating problems, one fix each**: (1) the file used to live at `/home/dev/.initial_password`, which filebrowser serves in full via `--root` — browsable/downloadable through the file manager, letting anyone with (even drifted, filebrowser-only) filebrowser access recover the real SSH/sudo password. Fixed by moving it to `/var/lib/claude-code-docker` (own bind mount, `DEV_SECRETS_PATH`), which filebrowser never touches — with automatic `mv`-based migration for existing deployments (not copy, so the exposed original doesn't linger). (2) The user then asked, correctly, why plaintext needed to be stored *at all* when `/etc/shadow` itself only ever stores a hash — moved to hash-only storage as described above. `entrypoint.sh` migrates both prior plaintext locations (`/home/dev/.initial_password` and the later `/var/lib/claude-code-docker/.initial_password`) automatically: reuses the existing plaintext once to derive+persist a hash, then deletes it, so an upgrade never silently resets the password.
- **PAM hook keeps the persisted hash in sync with live password changes** (`sync-dev-password-hash.sh`, wired into `/etc/pam.d/common-password`): entrypoint.sh only reapplies the persisted hash *at boot* — without this, an interactive `passwd`/`sudo passwd dev` change would work until the container was recreated, then silently revert to the stale persisted value. The hook is appended after `pam_permit.so` in the file's own documented "Additional block" for local hooks, as `password optional pam_exec.so seteuid /usr/local/sbin/sync-dev-password-hash.sh`. Two safety properties, both deliberate: `optional` means the hook's own result is completely ignored, so it can never block a login or password change even if it errors; and being placed after `pam_permit.so` (not before) means it only ever runs on the *success* path — a wrong-current-password `passwd` attempt hits `pam_deny.so`'s `requisite` first and the stack stops before reaching this line at all, so failed attempts can never corrupt the persisted hash. `seteuid` makes the script run with the PAM transaction's effective (root) privilege regardless of who invoked `passwd`, since `dev` itself has no write access to `DEV_STATE_DIR`. Verified end-to-end against a real container: `passwd` (dev's own) and `sudo passwd dev` (root-forced) both updated the persisted hash and survived a subsequent `docker rm` + recreate; a wrong-current-password attempt left the hash file byte-for-byte unchanged.
- **docker.sock access is sudo-gated, deliberately**: entrypoint.sh does *not* add `dev` to the socket's group. `dev`'s sudo already always requires a password (no NOPASSWD, see below) specifically so Claude Code can't self-elevate — putting `dev` directly in the socket's group would open the exact same bypass for `docker` (docker.sock access ≈ root on the host), letting Claude reach or disrupt real running containers on the NAS without a human ever entering a password. Docker is only usable via `sudo docker ...`, which still prompts every time; root always has access to the socket regardless of group membership, so no group setup is needed for that path.
- **SSH host keys**: generated under `/etc/ssh/host_keys` if missing.
- **filebrowser bootstrap**: creates a `dev` admin account (same password) on first run only, in a database kept outside `/home/dev`. filebrowser's minimum password length isn't hardcoded — it's `Settings.MinimumPasswordLength`, a DB-stored value defaulting to 12 (confirmed by reading filebrowser's actual source: `users/password.go`'s `ValidateAndHashPwd` takes it as a parameter, and `cmd/users_add.go` sources it from `s.MinimumPasswordLength`). Lowered to 8 via `filebrowser config init --minimumPasswordLength 8`, matching this project's own random-password length instead of forcing `DEV_PASSWORD` to be longer than it needs to be. Guards against the (now 8-character) minimum explicitly (skip + warn, not crash) — letting `filebrowser users add` fail here used to abort the whole entrypoint under `set -e` and take sshd/wetty/claude down with it. Note filebrowser separately also rejects common/easy passwords (`users/assets/common-passwords.txt`) regardless of length — caught this empirically when a test password like `eight888` was rejected with "password is too easy" even though it satisfied the length check.
- **Conditional `DISABLE_AUTOUPDATER`**: only set when `CLAUDE_CODE_VERSION` pinned a specific version at build time (via `/etc/claude-code-version-pin`); left alone for the default `latest` build so claude can self-update normally.

### SSH sessions vs. direct fork/exec: environment inheritance gotcha
Anything `entrypoint.sh` exports before `exec supervisord` reaches supervisord's direct children fine (wetty, filebrowser). It does **not** reach SSH login sessions — sshd's PAM-based session setup rebuilds the environment rather than inheriting sshd's own process env. Any variable that needs to be visible in an SSH shell must *also* be written to `/etc/environment` (see the `DISABLE_AUTOUPDATER` handling for the pattern). This cost real debugging time once; don't reintroduce the same bug for a new variable.

### Bind mounts, not named volumes — and why some paths are split out
All persistent state uses bind mounts to host paths from `.env` (`DEV_HOME_PATH`, `DEV_SSH_HOSTKEYS_PATH`, `FILEBROWSER_DATA_PATH`, `DEV_SECRETS_PATH`), chosen so the NAS admin can snapshot/back up the underlying folders directly. Three things are deliberately mounted *outside* `/home/dev` rather than nested under it, all for the same underlying reason — filebrowser serves `/home/dev` in full via `--root`, so anything nested under it is browsable/downloadable through the file manager UI, even in a dotfile subdirectory ("hide dotfiles" is a cosmetic UI setting, not real isolation):
- `/etc/ssh/host_keys` (not all of `/etc/ssh`) — mounting the whole directory would shadow the image's baked-in `sshd_config`/`sshd_config.d/dev.conf` with an empty host directory on first use.
- `/var/lib/filebrowser` (filebrowser's own account/settings DB).
- `/var/lib/claude-code-docker` (`.password_hash`, a hash of the dev account's password — never plaintext; see the password-resolution bullets above for the two-stage history of why this needed a migration path).

### Dev toolchain: system-wide C/C++, user-space nvm/pyenv for everything else
`docker.sock` is mounted for the user to deploy projects claude builds here, not for claude to drive Docker itself — actual development (compiling, running, testing) happens inside this container, so it needs real toolchains, unlike the original "control tower" framing. C/C++ (`build-essential`/`gdb`/`cmake`/`pkg-config`) is installed system-wide via apt at build time, since there's no meaningful "pick a version per project" concept for it here. Node and Python are different: nvm and pyenv are installed under `/etc/skel/.nvm` and `/etc/skel/.pyenv` (seeded into `/home/dev` the same way as the tmux `.bashrc` snippet — see the home-seeding caveat above) specifically so a version can be picked per project **without ever needing sudo**, consistent with the sudo-is-always-password-gated design elsewhere in this repo. No default Node/Python version is pre-installed; `nvm install`/`pyenv install` pull one on demand. pyenv also needed its documented Debian/Ubuntu "suggested build environment" apt packages (`libssl-dev`, `zlib1g-dev`, etc.) — without them `pyenv install` either fails or silently produces a Python missing modules like `ssl`/`sqlite3`.

**nvm's install script bug, worth remembering if touching this block again**: nvm's `install.sh` writes whatever `$NVM_DIR` was set to *at install time* literally into the profile snippet it appends — not a `$HOME`-relative path. Since the Dockerfile installs nvm with `NVM_DIR=/etc/skel/.nvm` (so the install lands in the right seed location), letting the script auto-write its snippet would hardcode `export NVM_DIR="/etc/skel/.nvm"` into `/etc/skel/.bashrc` — broken for every actual user, who needs `$HOME/.nvm`. Fixed by installing with `PROFILE=/dev/null` (suppress the script's own profile edit) and appending the correct `$HOME`-relative snippet manually instead. Caught by actually inspecting the built image's `/etc/skel/.bashrc` (`docker create` + `docker cp`, no need to even run the container) rather than trusting the install script's own success output.

Both were verified end-to-end against a real running container (not just presence checks): C/C++ via `gcc`/`g++`/`make`/`cmake`/`gdb --version`; nvm/pyenv via an actual SSH `-tt` login through an `expect` script (not `ssh host "cmd"`, which — like nvm/pyenv's usual caveat — never sources `.bashrc` at all, non-interactive-non-login shells don't, regardless of this container). The real path (interactive SSH → tmux auto-attach → pane shell) is what needed confirming, and does work.

### Two access methods with credentials (SSH and wetty share one), plus filebrowser as the odd one out
SSH (real Linux/PAM account) and filebrowser (its own BoltDB user table) are bootstrapped with the same password on first run but are **not** kept in sync afterward — changing one (`passwd`, or filebrowser's own UI) does not propagate to the other. wetty isn't a third credential store at all — see below.

**wetty replaced ttyd as the web terminal, specifically to fix ttyd's auth story.** ttyd just execs a local command (`tmux new-session -A -s main`) behind a pty — it has no persistent credential store of its own, so authenticating it at all (its old `-c dev:PASSWORD` HTTP Basic Auth, re-supplied every boot) meant keeping a plaintext password somewhere the container could read at boot, which is part of why a persisted plaintext password existed in the first place. Removing that auth (a prior iteration) left `TTYD_PORT` completely open to anyone who could reach it — a real regression, flagged and accepted as *temporary* pending a proper fix. wetty is a genuine **SSH client** running in the browser (`--ssh-host=localhost --ssh-port=22 --ssh-user=dev`), not a pty-exec tool — it connects to this same container's own sshd, so auth is real PAM/shadow, byte-for-byte identical to a normal SSH login. No separate credential store, no plaintext password stashed anywhere for it, and no root-privileged `login`+PAM trick needed either (an earlier alternative considered and rejected — would have required running the web-terminal process itself as root). wetty runs as `gosu dev`, same as ttyd did.

Consequence for `.bashrc`'s tmux auto-attach snippet: it now fires through exactly one code path (`$SSH_TTY` being set on a real SSH session) instead of two — ttyd used to bypass it entirely via its own `-W tmux new-session ...` argument, so a genuine SSH login and a ttyd session reached the same tmux session through two different mechanisms. With wetty, both paths are literally the same mechanism, since wetty *is* an SSH login.

**Verified with a real headless browser**, not just `curl`/logs (wetty's terminal renders to an xterm.js canvas, so there's nothing meaningful to fetch/read otherwise — see the Commands section above for the Playwright technique): loading the wetty page shows a real `dev@localhost's password:` prompt (username pre-filled via `--ssh-user`, confirming it's genuinely shelling out to `ssh`, not faking anything); a correct password produces a working shell with the tmux status bar visible (confirming the `.bashrc` auto-attach path above); a wrong password produces `Permission denied, please try again.` and re-prompts, exactly like a real terminal SSH session would.

**wetty 3.2.0 has a real upstream bug that breaks it outright over plain HTTP** (`wetty-security-patch.js`, replacing `build/server/socketServer/security.js` in the installed package post-`npm install`): its helmet-based security middleware computes `req.protocol` to correctly pick `ws://` vs `wss://` for the CSP `connect-src` directive, but doesn't apply that same check to `hsts` or `upgradeInsecureRequests` — both stay on regardless of protocol. Since this container has no TLS configured (no `--ssl-key`/`--ssl-cert` on the wetty command), that combination is self-defeating: the browser honors `upgrade-insecure-requests` and silently retries `wetty.js`/`wetty.css`/the websocket over `https://`, which nothing here answers, so the terminal page renders as broken unstyled HTML (a bare "reconnect" button, no xterm.js canvas) — and `Strict-Transport-Security` then caches "always use https for this host" in the browser for a year, so it keeps failing on repeat visits even after fixing the URL to `http://`. Diagnosed from a real user report (broken screenshot → browser console CORS-looking errors that were actually a failed TLS handshake against a plain-HTTP port → confirmed root cause by reading the actual response headers, which matched helmet's exact default header set) and confirmed by reading wetty's own source (no CLI flag or config file exposes these helmet options — `policies(allowIframe)` takes no other parameters). Fix: replace the installed file with a patched version that reuses wetty's own `req.protocol` check to drop `hsts`/`upgradeInsecureRequests` when serving over plain HTTP, leaving the original secure-by-default behavior untouched for a hypothetical future TLS setup. **Caught a self-inflicted mistake while implementing this**: the `COPY` destination path assumed `/usr/local/lib/node_modules/wetty/...` (the official `node:*-bookworm-slim` Docker image's npm-prefix convention, which is what an initial standalone test happened to use) — but this Dockerfile installs Node via NodeSource's apt setup script, whose npm prefix defaults to `/usr`, so the real path is `/usr/lib/node_modules/wetty/...`. `COPY` doesn't error on a novel destination path, it just silently creates it — so the first attempt built successfully and produced zero errors while doing nothing at all; the response headers still showed the bug. Caught by actually checking `npm root -g` inside the real built image rather than trusting the path from a differently-configured test container. Verified fixed via real HTTP response headers (`upgrade-insecure-requests` and `Strict-Transport-Security` both gone) and a full Playwright login flow afterward.

### getrandom() shim (`getrandom_shim.c`)
Bun — the runtime `claude` has been compiled with since `@anthropic-ai/claude-code` 2.1.113 — calls `getrandom(2)`, which doesn't exist on Linux kernels older than 3.17. Some Synology DSM platforms stay on kernel 3.10.x regardless of DSM version, so this is a real constraint, not a hypothetical. Confirmed via `nm -D` on the actual compiled `claude` binary that it imports only `syscall@GLIBC_2.2.5`, not `getrandom`/`getentropy` — i.e. Bun goes through the generic libc `syscall()` wrapper, which is what makes interception possible at all. The shim is an `LD_PRELOAD` library (compiled in the Dockerfile's builder stage, always active via `ENV LD_PRELOAD=...`) overriding both the `getrandom()` symbol and generic `syscall()`, falling back to reading `/dev/urandom` directly on `ENOSYS`. It does not log anything (an earlier version printed a stderr warning per-process, but since the shim is always active, hitting the fallback is the expected/routine case, not an exceptional one, so the logging was removed). On kernels that do have `getrandom(2)` this is a transparent no-op, so it's left on unconditionally.

A third path needed its own override: glibc >= 2.36's `arc4random()`/`arc4random_buf()`/`arc4random_uniform()` (confirmed via `nm -D /usr/sbin/sshd` showing them as undefined `GLIBC_2.36` symbols — `sshd` calls these directly). glibc's own implementation reaches `SYS_getrandom` via a raw `syscall` instruction inlined in its internal helper, not through the public `getrandom()` or `syscall()` symbols, so neither of the first two overrides ever sees that call. On `ENOSYS` glibc treats this as unrecoverable and aborts (`Fatal glibc error: cannot get entropy for arc4random`), which crashed sshd's per-connection child on affected kernels — sshd itself stayed up (only the forked child handling an actual login died), so this only surfaced when someone tried to SSH in, not at container-start smoke-test time. Since `arc4random*` are themselves normal exported dynamic symbols, overriding them intercepts the call before it reaches glibc's fragile internal path, sidestepping the raw syscall entirely. Reproduced and verified with the seccomp `ENOSYS` technique above plus an actual SSH login attempt (not just `claude --version`) — the failure mode only shows up on the per-connection path.

**Real-NAS crash, 2026-07-21 — SIGABRT on an sshd child despite the arc4random override already being in place, plus two more bugs uncovered while chasing it.** User's actual DS216+II hit `reaped unknown pid N (terminated by SIGABRT (core dumped))` on real SSH login attempts, even though `/proc/<sshd-master-pid>/maps` confirmed the shim `.so` was mapped into the master process. The suspicion (never directly proven via strace, but consistent with everything found afterward): `LD_PRELOAD` as an env var is exactly the kind of thing that can fail to propagate cleanly across some fork/exec paths inside sshd's connection handling (this repo already has a documented, *proven* instance of a related class of problem — SSH login sessions not inheriting entrypoint.sh's exported env because PAM rebuilds it — so treating env-var propagation into arbitrary sshd-internal process transitions as fragile-by-default was the reasonable prior). Fix: also install the shim via `/etc/ld.so.preload`, which the dynamic linker reads directly off disk for every dynamically linked executable, with no dependency on any environment surviving anything. `RUN echo /usr/local/lib/getrandom_shim.so > /etc/ld.so.preload`, right after the existing `ENV LD_PRELOAD=...` (kept for defense in depth, no downside to both).

That fix immediately surfaced two more, previously-masked bugs — found via `strace -f` against the real `/usr/sbin/sshd` binary under the seccomp `ENOSYS` simulation, not guessed:

1. **`getentropy()` — a fourth uncovered path, this time crashing the *master*, not just a connection child.** `nm -D /lib/x86_64-linux-gnu/libcrypto.so.3` shows an undefined `getentropy@GLIBC_2.25` import — OpenSSL 3.x seeds its own PRNG through this, not `getrandom()`/`syscall()`/`arc4random*`, so it sailed past every existing override. Unlike arc4random's abort, OpenSSL just logs `PRNG is not seeded` and the process exits — and since sshd's *master* calls this during its own early startup (not just per-connection children), this killed the master outright, before it could even listen. Fixed by adding a `getentropy(void *buffer, size_t length)` override alongside the others, backed by the same fallback path (256-byte cap preserved for contract compatibility with the real glibc function, per `man getentropy`).

2. **Even with `getentropy()` covered, a *second*, independent bug remained: per-connection children still died, now with `SIGSYS` instead of `SIGABRT`.** Root cause, again only found via `strace -f`: sshd applies its own internal seccomp-BPF sandbox to the pre-auth, per-connection child — a real, independent OpenSSH hardening feature (nothing to do with Docker/container-level seccomp, and no longer even configurable off via `sshd_config`'s `UsePrivilegeSeparation`, which modern OpenSSH — 9.2 here — has removed as a directive entirely; sandboxing is unconditional now). That sandbox's syscall allowlist has no reason to include `open()`/`openat()` — a healthy sshd never opens new files at that point — so this shim's *lazy, open-a-fresh-fd-every-call* fallback got the whole process killed the moment it tried.

   The natural fix — open `/dev/urandom` once, eagerly, in a `__attribute__((constructor))`, before any of this can happen — turned out to be its own dead end, discovered via the *same* `strace -f`: sshd's master calls `close_range(3, ~0, 0)` early in its own startup (a real, independent OpenSSH hardening step, unconditionally closing every fd above 2 with no regard for who opened it or why). A constructor runs *before* that, so whatever fd it grabbed was already gone by the time anything needed it — first symptom was the fd landing on a colliding low number and the master itself failing with the same "PRNG is not seeded" as bug 1 above; moving the fd to a high number via `fcntl(F_DUPFD, 512)` didn't help either, still `EBADF` — because `close_range` doesn't care what number the fd has, it kills everything above 2 regardless.

   **The design that actually works**, verified via `strace -f` line-by-line: open `/dev/urandom` *lazily*, the first time a fallback is actually needed — which in practice happens early in the master's own startup (OpenSSL's `getentropy()` call above), safely *after* `close_range` has already run — and then **cache the fd and never close it**, reusing the same one on every subsequent call. Caching (not closing) means that when sshd later `fork()`s a per-connection child, the child inherits that already-open, already-valid fd as part of the normal fd-table duplication fork() does — so the child's own fallback calls never need to call `open()` at all, sidestepping the sandbox's restriction entirely instead of trying to get past it. `getrandom_shim.c`'s `fallback_getrandom()` is exactly this: no constructor, no dup-to-high-number, just `if (urandom_fd < 0) urandom_fd = open(...)` and reuse. Verified end-to-end under the seccomp `ENOSYS` simulation: `strace -f` shows the master's own `getentropy` call succeeding via the cached fd (no more "PRNG is not seeded"); four consecutive real SSH logins all succeed cleanly (`Accepted password for dev`, no SIGABRT/SIGSYS in the logs); a full Playwright wetty login (real SSH client, separate code path) also succeeds end-to-end under the same simulation.

`CLAUDE_CODE_VERSION` is an independent, secondary fallback for the same underlying problem: pinning to `2.1.112` or earlier installs the last pre-Bun, plain-Node.js `claude` build, sidestepping the issue entirely without needing the shim.

### Deployment target assumption
Meant to run directly on the target NAS's own Docker daemon via a bind-mounted `/var/run/docker.sock` — not a remote/SSH-based Docker context. This was a deliberate, previously-revisited decision (an SSH-remote-control redesign was started once and then reverted at the user's request); don't propose switching it without the user raising it first.

### Networking: the real `bridge` network, via `network_mode`, not compose's own network
`docker-compose.yml` uses `network_mode: bridge` on the service rather than leaving compose to auto-create its usual project-scoped network (`claude-code-docker_default`). Deliberate, so this container ends up on the same network as everything else the user runs through Synology Container Manager (which defaults new containers to the literal `bridge` network) — needed for the user's planned future Authentik container to reach this one (by IP, or via Container Manager's "링크" UI feature, which is Synology's wrapper around Docker's legacy `--link`). The obvious-looking alternative — `networks: [default]` plus a top-level `networks: default: {name: bridge, external: true}` — fails outright: `invalid config for network bridge: invalid endpoint settings: network-scoped aliases are only supported for user-defined networks`. Docker's literal built-in `bridge` network (unlike a user-defined one, including compose's own auto-created ones) doesn't support the per-container aliases compose tries to set when you reference a network by name in a service's `networks:` list — `network_mode: bridge` sidesteps this because it doesn't go through that alias-setting code path at all. Verified with a real `docker compose up`: container attached to `bridge` (confirmed via `docker network inspect bridge`, listed alongside another pre-existing container on the same host) and booted normally.
